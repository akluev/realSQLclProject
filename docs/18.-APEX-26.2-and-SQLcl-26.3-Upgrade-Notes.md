# APEX 26.2 & SQLcl 26.3 Upgrade Notes

These notes cover only what is **different** from the 26.1 upgrade. For everything
else (worktree, clone database, baseline export, validation, cut-over), follow the
[APEX 26.1 & SQLcl 26.1 Upgrade Guide](16.-APEX-26.1-and-SQLcl-26.1-Upgrade-Guide.md).

> **One change to the 26.1 process: the cut-over now ends by re-importing every APEX
> application into production.** In the 26.1 process, PROD is synchronized
> (`prj_sync`, `lb changelog-sync`): the baseline applications are recorded as deployed
> but not installed, so PROD keeps its original imports, with the issues the upgrade
> fixed. Other environments install the baseline normally and get the corrected
> applications without extra steps. So after the final `prj_sync` and the deployment of
> the pending changes, force a redeploy of all applications in PROD.
> See [section 4](#4-finish-re-import-all-apex-applications-into-production).

Four changes are required:

1. **Export:** stop exporting APEX applications as readable YAML.
2. **Stage:** work around two SQLcl 26.3 bugs in the APEX changesets.
3. **Import:** remove obsolete Universal Theme styles (such as Vista) that make the
   APEX 26.2 import fail with ORA-20987.
4. **Finish:** re-import every APEX application into production, not only the changed ones.

One optional change is also worth making: [`stage.change.changeStyle`](#5-optional-stagechangechangestyle-is-now-documented)
is now an officially documented setting.

---

## 1. Export: remove `READABLE_YAML`

In `.dbtools/project.config.json`, remove `READABLE_YAML` from the APEX export types:

```diff
     "apex" : {
-      "exptype" : [ "READABLE_YAML", "APPLICATION_SOURCE" ],
+      "exptype" : [ "APPLICATION_SOURCE" ],
```

APEX application source is now maintained as APEXlang only. Export each application
with the `prj_exp_app <app_id>` alias, which runs
`apex export -exptype APEXLANG` into `src/database/<schema>/apex_apps/f<app_id>`.
Then validate each one with `prj_validate <app_id>`.

## 2. Stage: two SQLcl 26.3 workarounds

### 2.1. APEX changeset checksum is not updated

**Bug:** when `project stage` regenerates `dist/releases/apex/f<app_id>/f<app_id>.sql`,
it does **not** update the `-- sqlcl_checksum` line in the matching `f<app_id>.xml`
([Oracle forum post](https://forums.oracle.com/ords/apexds/post/sqlcl-26-3-projects-not-updating-the-apex-xml-sqlcl-checksu-8305)).
Up to SQLcl 26.1 the value was an epoch-millisecond timestamp that changed on every
stage. Since 26.2 it is the SHA-1 of `f<app_id>.xml` itself (without the checksum line),
so it stays the same when only `f<app_id>.sql` changes. The XML changeset is then
unchanged, Liquibase does not rerun `INSTALL_<app_id>`, and **the changed application is
silently not deployed**. Oracle confirmed the bug in the forum thread (November 2026) and
said it is fixed for the next release. Regression test
[024](../regression/tests.md) checks for it.

The stale checksum is itself the bug, and fixing the line by hand creates a second
problem: SQLcl now sees the XML as manually edited, and the next stage stops with:

```text
SQL> project stage

Stage is Comparing:
Old Branch      refs/heads/main
New Branch      refs/heads/apex-26.2-app-fix

ERROR: An error has occurred processing your request:
The generated APEX install file dist\releases\apex\f407\f407.xml has been edited and stage will not overwrite it automatically.
Restore the generated file, remove it, or merge your edits manually before running stage again.
```

**Workaround:** when APEX applications changed, run `prj_apex_stage` instead of
`project stage`. The alias:

1. deletes `dist/releases/apex/f*` so stage can regenerate the files without complaint;
2. runs `project stage`;
3. runs `scripts/bash/fix-apex-checksums.sh`, which copies the hash from the
   `-- sqlcl_snapshot` trailer of each `f<app_id>.sql` into the `-- sqlcl_checksum`
   line of `f<app_id>.xml`.

deletes all `dist/releases/apex/f*` folders, so stage regenerates every application's
files, and every regenerated XML comes back with the stale checksum. This is
normal; the only result to worry about is `errors` above 0. Review `git diff` as
usual before committing.

**To adopt it in your repository:**

- Copy [`scripts/bash/fix-apex-checksums.sh`](../scripts/bash/fix-apex-checksums.sh)

  Run `fix-apex-checksums.sh --dry-run` to see what it would change.
- The `prj_apex_stage` alias is in [`scripts/xml/sqlcl-project-aliases.xml`](../scripts/xml/sqlcl-project-aliases.xml),

  SQL> alias save

  See [Common Commands and Directives, section 1](12.-Common-Commands-and-Directives.md#1-sqlcl-aliases)
  and [SQLcl Project aliases](https://alexonapex.com/blog/2026/08/13/sqlcl-project-aliases/)
  for how the aliases work.

### 2.2. Forward vs. backward slashes in `DATABASECHANGELOG.FILENAME`

**Symptom:** after the upgrade, `prj_status` (`lb status`) lists **every** APEX
`INSTALL_<app_id>` changeset as pending, including applications that were
installed recently. Deploying does not clear them: after every deployment they are
pending again.

**Cause:** up to SQLcl 26.1, the generated APEX changeset had no `logicalFilePath`:

```xml
<changeSet id="INSTALL_102" author="SQLCL-Generated"  failOnError="true"   runOnChange="true" >
```

Liquibase therefore recorded the physical path in `DATABASECHANGELOG.FILENAME`, with
the path separator of the operating system that ran the deployment. Deployed from
Windows, that is `releases\apex\f102\f102.xml`; from macOS or Linux,
`releases/apex/f102/f102.xml`. Since SQLcl 26.2 the changeset sets an explicit
logical path that always uses forward slashes:

```xml
<changeSet id="INSTALL_102" author="SQLCL-Generated" logicalFilePath="releases/apex/f102/f102.xml"  failOnError="true"   runOnChange="true" >
```

This is the real fix for mixed Windows and macOS/Linux teams: the recorded name no longer
depends on who deploys. But rows written from Windows before the upgrade still have
backslashes, and Liquibase does not repair them:

- Liquibase does not treat the changeset as new, so it never inserts a second row with
  the forward-slash name.
- When it reruns the changeset (`runOnChange`), its update of the existing row matches the
  filename exactly, so the backslash row is never updated. Its checksum stays old.

**This is not a one-time redeploy.** The row never changes, so every deployment installs
every affected application again, for as long as the old rows stay as they are. The
same mechanism caused SQLcl 25.4.1 to redeploy APEX applications every time on Windows
([regression test 017](../regression/tests.md)).

**Fix:** normalize the old rows once. Add a custom changeset (`project stage add-custom -file-name update_apex-changelogs.sql`)
that normalizes the existing rows before the APEX changesets run:

```sql
prompt 'Updating APEX apps databasechangelog filenames to use forward slashes'

update databasechangelog
set filename = replace(filename,'\','/')
where author = 'SQLCL-Generated'
and id like 'INSTALL%'
and filename != replace(filename,'\','/')
;
```

The update is idempotent. Once it has been deployed to every environment, it has nothing
left to change. Environments deployed only from macOS or Linux already have forward
slashes, so nothing is updated there.

## 3. Import: ORA-20987 for obsolete Universal Theme styles

**Symptom:** deploying an application to an APEX 26.2 instance (`prj_install`,
`lb update`) fails with:

```text
ERROR at line 1:
ORA-20987: APEX - Component with Static ID "4007676303523989775" can not be found in the application . Please ensure a component with the same Static ID exists in the master application and try again.
Alternatively, you can set the "Subscription Mode" as "Ignore Errors", to ignore invalid master component references.
ORA-06512: at "APEX_260200.WWV_FLOW_ERROR", line 1186
ORA-06512: at "APEX_260200.WWV_FLOW_ERROR", line 1251
ORA-06512: at "APEX_260200.WWV_IMP_UTIL_INT", line 3307
ORA-06512: at "APEX_260200.WWV_IMP_UTIL", line 129
ORA-06512: at line 85
Help: https://docs.oracle.com/error-help/db/ora-20987/
Unable to rollback Scripts automatically, taking no action.
```

**Cause:** the application has a theme style **subscribed** to a Universal Theme
master component that APEX 26.2 no longer ships. The style itself is not the
problem. The import fails on `wwv_imp_util.get_subscription_id`, when it looks up the
master component by the Static ID in the error message. In our case it was the old
**Vista** style:

```sql
wwv_flow_imp_shared.create_theme_style(
 p_id=>wwv_flow_imp.id(8233414511837841)
,p_theme_id=>42
,p_name=>'Vista'
,p_static_id=>'vista'
,p_css_file_urls=>'#THEME_IMAGES#css/Vista#MIN#.css?v=#APEX_VERSION#'
,p_is_public=>false
,p_is_accessible=>false
,p_theme_roller_read_only=>true
,p_reference_id=>wwv_imp_util.get_subscription_id(4007676303523989775,2010,wwv_flow_t_varchar2(),null)
);
```

Many applications have the Vista style without that subscription. They import
without errors, and you can still switch them to Vista. So do not search by style
name. Search by the Static ID from the error message instead. In our repository,
12 applications have a Vista style, but only 4 reference the missing master component:

```text
$ grep -l "p_name=>'Vista'" dist/releases/apex/f*/f*.sql
dist/releases/apex/f100/f100.sql
dist/releases/apex/f102/f102.sql
dist/releases/apex/f104/f104.sql
dist/releases/apex/f110/f110.sql
dist/releases/apex/f114/f114.sql
dist/releases/apex/f116/f116.sql
dist/releases/apex/f165/f165.sql
dist/releases/apex/f1968/f1968.sql
dist/releases/apex/f202/f202.sql
dist/releases/apex/f205/f205.sql
dist/releases/apex/f300/f300.sql
dist/releases/apex/f401/f401.sql

$ grep -l "4007676303523989775" dist/releases/apex/f*/f*.sql
dist/releases/apex/f102/f102.sql
dist/releases/apex/f165/f165.sql
dist/releases/apex/f300/f300.sql
dist/releases/apex/f401/f401.sql
```

Only the applications in the second list need the fix below.

**What does not help:**

- The "Subscription Mode = Ignore Errors" hint in the error message.
  `apex_application_install.set_subscription_mode` cannot be called, because SQLcl
  generates the install changeset.
- `"expSubscriptions" : false` in `project.config.json`: subscriptions are exported anyway.
- The instance parameter `IMP_DEFAULT_SUBSCRIPTION_MODE`
  ([`SET_SUBSCRIPTION_MODE`](https://docs.oracle.com/en/database/oracle/apex/26.1/aeapi/APEX_APPLICATION_INSTALL.SET_SUBSCRIPTION_MODE-Procedure.html)).
  We tested every mode, including ignore errors, remove and legacy. Missing or
  deprecated Universal Theme styles are not affected, and the import still fails:

  ```sql
  begin
    apex_instance_admin.set_parameter(
      p_parameter => 'IMP_DEFAULT_SUBSCRIPTION_MODE',
      p_value     => apex_application_install.c_subscription_legacy);
    commit;
  end;
  /
  ```

**Fix:** remove the obsolete style from the application source:

1. In App Builder, open each affected application: **Shared Components → Themes →
   Universal Theme → Styles**, delete **Vista**, and save.
   (Editing the APEXlang source should also work; we did it in App Builder.)
2. Re-export with `prj_exp_app <app_id>`, validate with `prj_validate <app_id>`,
   commit, and run `prj_apex_stage`.

This keeps all other subscriptions intact. That matters if, like us, you re-baseline
from production after every APEX upgrade and want subscriptions to carry over to DEV.

## 4. Finish: re-import all APEX applications into production

**This is a change to the 26.1 process.** Each upgrade starts by taking a baseline
from production. After the 26.1 upgrade, only the applications that changed later
were redeployed to production. The others stayed as originally imported, still
carrying the issues fixed during the 26.1 upgrade (APEXlang export bugs, obsolete
theme styles). When the 26.2 upgrade branch was rebased on production, those
issues came back, together with the new checks that APEX 26.2 runs on import.

To avoid that next time, the upgrade now ends by re-importing **every** APEX application
into production. Do it after the final `prj_sync` and after all outstanding changes
have been deployed.

Only PROD needs this step. It is the only environment that is synchronized with
`prj_sync` instead of deployed. Every other environment installs the baseline
applications through the normal deployment.

1. Run `prj_force_apex`. It removes the Liquibase records of all APEX application
   installs, so Liquibase treats every `INSTALL_<app_id>` changeset as not yet run:

   ```text
   SQL> prj_force_apex
   This will FORCE re-deployment or synching of APEX application even if no changes detected. Press ENTER to continue or Ctrl-C to cancel...

   Done. Run 'prj_install' to re-install APEX applications or 'prj_sync' to update the catalog now.
   ```

2. Run `prj_install` to redeploy all applications.

The alias, from
[`scripts/xml/sqlcl-project-aliases.xml`](../scripts/xml/sqlcl-project-aliases.xml):

```xml
<alias name="prj_force_apex">
    <description/>
    <queries>
        <query minversion="8">
            <sql><![CDATA[
pause This will FORCE re-deployment or synching of APEX application even if no changes detected. Press ENTER to continue or Ctrl-C to cancel...
delete FROM databasechangelog_actions
    where ID like 'INSTALL\_%' escape '\'
    and author ='SQLCL-Generated'
    and filename like 'releases_apex_f%_f%.xml'
    and description like 'runApexScript%' ;
delete from databasechangelog
where ID like 'INSTALL\_%' escape '\'
and author ='SQLCL-Generated'
and filename like 'releases_apex_f%_f%.xml'
and description like 'runApexScript%';
commit;
prompt Done. Run 'prj_install' to re-install APEX applications or 'prj_sync' to update the catalog now.
]]></sql>
        </query>
    </queries>
</alias>
```

The unescaped `_` in `releases_apex_f%_f%.xml` matches any single character, so the
alias matches filenames recorded with either forward or backward slashes (see [2.2](#22-forward-vs-backward-slashes-in-databasechangelogfilename)).

## 5. Optional: `stage.change.changeStyle` is now documented

`stage.change.changeStyle` controls how `project stage` builds changesets from a
generated file:

- `multiple`: each statement becomes its own changeset.
- `single`: all statements go into one changeset.

Before SQLcl 26.3 the setting was undocumented, so relying on it was a gray area.
It is now listed by `project config`, so we set it explicitly in
`.dbtools/project.config.json`:

```json
  "stage" : {
    "excludeObjects" : [ "ALL.user" ],
    "generatedFormat" : "liquibase",
    "softObjectIsolation" : "change",
    "change" : {
      "changeStyle" : "multiple"
    }
  }
```
