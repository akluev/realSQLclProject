# Upgrade ORDS and APEX Images on a VM

**Edit the launcher at `/home/oracle/bin/ordsstart`.** After database `FREE` starts, `/etc/rc.d/init.d/oracle-free-26ai` switches to the `oracle` user, sources `~/.bashrc`, and calls `~/bin/ordsstart`. This is where the VM gets its APEX images path on every boot.

The November 2026 upgrade moved the ORDS database schema in `FREEPDB1` from 26.1.2 to 26.3.1. The launcher used `~/ords-latest`, while the schema upgrade was run from a separate copy in `~/ords`. For the next upgrade, use the product directory named in the launcher for both operations.

## VM Reference

These values describe the VM used for the November 2026 upgrade. This guide covers upgrading ORDS and switching the static images path after an APEX upgrade; it does not install or upgrade APEX in the database.

| Item | Recorded value |
| --- | --- |
| Operating-system user | `oracle` |
| Database / PDB | `FREE` / `FREEPDB1` |
| ORDS schema upgrade | 26.1.2 to 26.3.1 |
| ORDS product directory used by the launcher | `/home/oracle/ords-latest` |
| ORDS configuration directory | `/home/oracle/ords_config` |
| Database pool | `default` |
| Boot service / script | `oracle-free-26ai.service` / `/etc/rc.d/init.d/oracle-free-26ai` |
| ORDS launcher | `/home/oracle/bin/ordsstart` |
| Standalone HTTP port | `8080` |
| APEX images directory after the switch | `/home/oracle/apex_26.2_en/apex/images` |
| Runtime log pattern | `/tmp/ordslogoracle*` |

## Switch to a New APEX Images Directory

As `oracle`, open the launcher:

```sh
vi ~/bin/ordsstart
```

The command recorded after the switch to APEX 26.2 was:

```sh
#!/bin/bash
export WHOAMI=`whoami`
nohup /home/oracle/ords-latest/bin/ords --config /home/oracle/ords_config serve --port 8080 --apex-images /home/oracle/apex_26.2_en/apex/images > /tmp/ordslog$WHOAMI$$ 2>&1 &
```

For the next APEX release, change the directory after `--apex-images` to the actual extracted `apex/images` directory. Check its `apex_version.txt` against the APEX release installed in the database. The launcher serves those files directly, so changing the path requires only an ORDS process restart. If you are also upgrading ORDS, do that before starting it again.

## Upgrade ORDS in Place

Run as `oracle`. Confirm that the launcher still uses `~/ords-latest/bin/ords`, then download and test the archive before stopping anything:

```sh
cat ~/bin/ordsstart
curl -fL -o ~/ords-latest.zip https://download.oracle.com/otn_software/java/ords/ords-latest.zip &&
  unzip -tq ~/ords-latest.zip
```

Identify the standalone Java process by its WAR, port, and images path:

```sh
pgrep -af -u oracle 'ords[.]war.*serve.*--port 8080'
```

Run `kill PID` with the numeric PID from that output. Repeat the lookup and wait until the old process exits. Leave the database running. If upgrading ORDS, run:

```sh
unzip -oq ~/ords-latest.zip -d ~/ords-latest &&
  ~/ords-latest/bin/ords --version &&
  ~/ords-latest/bin/ords --config ~/ords_config install -i --db-only
```

Select the existing `default` pool and confirm it points to `FREEPDB1`. Wait for the upgrade-complete message. The installer prints its log filename (under `~/logs` during the 26.3.1 upgrade).

## Start and Verify

Use the same launcher that runs at boot:

```sh
~/bin/ordsstart
pgrep -af -u oracle 'ords[.]war.*serve'
ls -lt /tmp/ordslogoracle* | head
```

The launcher redirects stdout and stderr to `/tmp/ordslogoracle<PID>`. The suffix is the launcher shell's PID. Once ORDS is listening, verify the images version actually served on port 8080:

```sh
curl -fsS http://localhost:8080/i/apex_version.txt
```

## How We Traced ORDS Back to the Boot Script

1. Inspect the boot-started process. Its arguments reveal the product directory, config directory, port, and images path. Its cgroup identifies the session that launched it.

   ```sh
   pid=$(pgrep -o -u oracle -f 'ords[.]war.*serve')
   ps -ww -p "$pid" -o pid,ppid,lstart,args
   cat "/proc/$pid/cgroup"
   systemctl status "$pid" --no-pager
   ```

2. On this VM, the parent PID was 1 and the cgroup was `session-c4.scope`. The boot journal showed `oracle-free-26ai` announcing that database `FREE` had started, printing its ORDS startup message, then opening an `su` session as `oracle` at the same second the Java process started.

   ```sh
   sudo journalctl -b -u oracle-free-26ai.service --no-pager
   ```

3. Search for the distinctive journal message in the startup files. The surrounding lines expose the exact command:

   ```sh
   sudo grep -rInF -C 5 -- 'Starting up ords needs to be explicitly killed' /etc 2>/dev/null
   ```

   The match was in `/etc/rc.d/init.d/oracle-free-26ai`, line 152 at the time. Its command was `$SU -s /bin/bash $ORACLE_OWNER -c ". ~/.bashrc;~/bin/ordsstart"`. Following that call located both the persistent images argument and the runtime log redirection.
